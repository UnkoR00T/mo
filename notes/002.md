# 002_net.md

### Rola
`fv/p.java` to zaciemniona klasa **okhttp3.Dispatcher** (biblioteka OkHttp; widoczne pola `readyAsyncCalls`, `runningAsyncCalls`, `runningSyncCalls`, `maxRequests`, `maxRequestsPerHost`, `idleCallback`). Zarządza pulą asynchronicznych połączeń HTTP i ich współdzieleniem per-host. Brak logiki aplikacji mObywatela.

### Endpointy
brak

### Modele danych
- `fv.p` -> `okhttp3.Dispatcher` (biblioteka): `idleCallback: Runnable`, `executorServiceOrNull: ExecutorService`, `maxRequests: int = 64`, `maxRequestsPerHost: int = 5`, `readyAsyncCalls: ArrayDeque<kv.e.a>`, `runningAsyncCalls: ArrayDeque<kv.e.a>`, `runningSyncCalls: ArrayDeque<kv.e>` (plik: `fv/p.java`)
- `kv.e` -> `okhttp3.Call` (biblioteka), `kv.e.a` -> `okhttp3.AsyncCall` (wewnętrzna podklasa `RealCall`) - brak w tej paczce

### Logika
- `maxRequests=64`, `maxRequestsPerHost=5` - domyślne limity OkHttp (potwierdzenie, że to biblioteka, nie tuning aplikacji) (plik: `fv/p.java`)
- `h()` (promoteCallsToRunning): pod warunkiem `runningAsyncCalls.size() < maxRequests` i `callsPerHost < maxRequestsPerHost` przenosi wywołania z `readyAsyncCalls` do `runningAsyncCalls` i uruchamia przez `executorService` (plik: `fv/p.java`)
- `c()`: leniwie tworzy `ThreadPoolExecutor(0, MAX_VALUE, 60s, SynchronousQueue, "okhttp Dispatcher" - faktycznie `gv.d.f77111i + " Dispatcher"`), puli nie kasuje (brak `evictAll`) (plik: `fv/p.java`)
- `d(host)`: znajduje istniejące wywołanie do tego samego hosta (`fr.t.c(url.host, host)`) i współdzieli je zamiast otwierać nowe połączenie; pomija połączenia WebSocket (`getForWebSocket()`) (plik: `fv/p.java`)
- `e(...)`: po zakończeniu wywołania uruchamia `idleCallback`, o ile pula nie jest już bezczynna (plik: `fv/p.java`)
