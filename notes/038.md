### Logika
- `i(request, eventListener)`: bramka błędu - `eventListener.c(request)` + `request.getListener().c(request)` (plik: `kc/w.java`)
- `j(ErrorResult, target, eventListener)`: dla targetu View wybiera `TransitionFactory.k(request).a(target, result)`; jeśli zwrócono `Transition.NONE` -> tylko `target.c(image)`, inaczej event `r` (przed), `transition.a()`, event `q` (po); potem `eventListener.d(request, result)` + `listener.d(...)` (plik: `kc/w.java`)
- `k(SuccessResult, target, eventListener)`: identycznie dla sukcesu przez `target.b(image)` i `eventListener.a(...)` (plik: `kc/w.java`)
- `a()`/`e()` zwracają leniwe cache z `Options` (`options.d()`/`options.h()`), `b()` zwraca `Defaults` (plik: `kc/w.java`)
- `c(request)` liczy klucz pamięciowy w `options.g()` (główny dispatcher) - blokująco; `d(request, cont)` sprawdza `a0.d(request)` (czy ustawiono klucz pamięciowy): jeśli tak - `enqueue` przez `q0.e` (async), jeśli nie - `g(request, 1, cont)` (suspend) (plik: `kc/w.java`)
- `SuccessResult.getDataSource()` tylko odczytywane (raportowane do `EventListener`) (plik: `kc/w.java`)
